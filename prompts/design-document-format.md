ARCHITALK DOCUMENT FORMAT: smartmd-v1

Produce ONE self-contained Markdown string. It is saved/exported as the same document, including its diagrams. Adapt its depth, scenario count and terminology to the actual project; do not assume a website, SaaS, payment, authentication, load or business policy. Distinguish sourced facts, proposals, assumptions and unknowns. Unknown UI scope is not proof that no UI exists; identify the needed validation and clearly label any proposed UI. Never invent confirmation, endpoints, files, screenshot evidence, or links. Do not include local absolute paths to guides or installed tools.

SmartMD is required, using these supported forms OUTSIDE code fences:
- Begin at the first byte with YAML scalar frontmatter delimited by `---` lines. Include nonempty `title`, `locale` (`ko` or `en`) and `style: smartmd`. Use LF newlines.
- Include at least one nonempty `:::info title="..."` or `:::warning title="..."` callout, closed by its own `:::` line, for scope, assumptions or uncertainty. No nested directives.
- Include a SmartMD table specification immediately before a real GFM table. Example:
  {table caption="Requirements and evidence" columns=[{title="Requirement", align=left, width=60%}, {title="Evidence / status", align=left, width=40%}]}
  | Requirement | Evidence / status |
  | --- | --- |
  | Actual requirement | Actual source reference or explicit unknown |
  Column specifications correspond to table columns in order. Do not put the table in a code block.

Include these exact level-2 headings (English headings are stable identifiers; explain in the response language):
`## Navigation`, `## Jobflow`, `## State`, `## Screen Layout`.
Use the actual lowercase `navigation`, `jobflow`, `state`, `layout` fenced languages in their own sections, each with a closed, nonempty block of the dedicated DSL. Opening and closing dedicated fences start at column zero, with the language immediately after the opening backticks. Mermaid may supplement a context/component view but MUST NOT replace these four DSLs. Do not put demonstration fences inside another fence. Do not add unrecognized DSL controls or comments inside DSL blocks.

NAVIGATION: Model user-visible pages/overlays and only the API/process/data needed to determine movement. Each independent user task has its own subheading, diagram, short prose describing entry, success, relevant failure/cancel/retry/return, then `### 화면 확인 링크` (or `### Screen verification links`) and a table `페이지·장면 | 화면 HTML | Layout` (English equivalents permitted). Link Layout cells to actual headings in THIS Markdown document, using their real heading anchors. This single-document output does not generate HTML assets: record `확인 불가 — 화면 HTML 미생성` (English equivalent allowed) when no actual screen exists; never invent .html links. Each scenario lists its own relevant pages, including failure/return pages. A task with no movement uses prose and the same screen-links table rather than fake self-arrows; the section still includes DSL for any actual movement.
Syntax: `Page --> OtherPage : action`, `Page --> (validate_input)`, `(validate_input) --> (/actual_api) : valid`, `(/actual_api) --> Page : error`; backtick-wrapped data is allowed. Separate labels with spaces around ` : `. Use simple navigation/state node names without square/curly brackets, pipe or semicolon; describe complex values outside the DSL. Only pages, `(process)`, `(/api)` and backtick data are navigation nodes; no User/Browser/Email actor or event node. A direct URL entry starts at the destination page or a deciding process; explain the entry in prose. Logical API names map to sourced actual contracts outside the block; proposed APIs must be labelled proposals. Keep separate navigation scenarios readable.

JOBFLOW: Describe the project's real or explicitly proposed component cooperation. Use `orchestrator: Coordinator` for a coordinating owner, or `scope: public cooperation` for a boundary view; these are different meanings. Declare every object in `Object: A, B, C`, ordered to reduce crossing. Lines are `Object.Method --> Other.Method`, `Object.OnEvent --> Other.Method`, `Object.Check.true --> Store.Save`, or `Object.message.Request --> Other.message.Response`. Do not add arrow labels, parameters or arbitrary control tokens. Explain each arrow immediately below in one short bullet, in declaration order (method-to-own-result lines are the sole exception). Distinguish calls, events, returned results and boundary messages; never infer private internals or automatic business effects.

STATE: Separate independent owners/lifecycles. State the owner, initialization, transition inputs and invariants beside each block. Syntax: `<s> --> (Ready)`, `(Ready) --> (Running) : input`, `(Running) --> (Failed) : failure`, `(Failed) --> (Ready) : retry`. `<Event>` is an event, plain text an action. `<e>` or `.` means an actual lifetime end; do not invent termination of a continuing service. Describe applicable failure/cancel/timeout and forbidden inputs. Keep conditions and results consistent with navigation/jobflow.

SCREEN LAYOUT: Inventory the applicable pages and important scenes, with real headings whose anchors navigation tables use. Each page's `layout` block is a single connected tree: `Screen V Header, Main, Footer`, `Main > Sidebar : 25, Content : 75`, `Content V Input, Result`. ` V ` is vertical; ` > ` is horizontal; children are comma-separated. No H operator, cycles, duplicate containers, multiple parents or disconnected roots. Numbers are optional horizontal flex weights without `%`, not exact pixels; vertical sizes are ignored. Explain input, action, feedback, error/empty/loading scenes and relevant responsive/accessibility behavior as project proposals or facts.

APPLICABILITY EXCEPTIONS: Jobflow and State always need meaningful DSL. If the project explicitly has no graphical UI, Navigation and Screen Layout each retain their heading and may replace DSL with these three standalone fields, values in the response language:
Applicability: not_applicable
Reason: a concrete source-grounded explanation of why this project has no pages/screens
Alternative interface: the actual or explicitly proposed CLI/API/batch/operator interface and its interaction or contract
Do not use bare N/A, a missing diagram, or unknown UI as this exception. A confirmed UI confined to a single page with no navigation may use the same fields in Navigation only, explaining that all tasks remain on that page and linking its actual Layout section; Screen Layout still needs its DSL.

CRITIC: Apply this same format contract to new documents, checking section/DSL/SmartMD presence, applicability evidence, scenario screen links and consistency with actual sources. Report concrete omissions or unsupported claims with counterexamples; do not require a fake UI or more diagrams than project scope needs. Older drafts lacking this contract are historical documents; do not claim they were produced under smartmd-v1.
