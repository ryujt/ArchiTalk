ARCHITALK DESIGN PACKAGE: architecture-package-v1

Create a connected set of engineering design documents, not a brief summary split across filenames. Start from business goals and evidence, identify architecture drivers, make quality expectations observable, explore materially different tactics/styles/patterns, compare their trade-offs, propose decisions, record ADRs and connect them to verification. Technology names are possible means, never the starting requirement.

Follow the TASK's output envelope: a complete-package task returns one JSON object with `markdown` (the principal architecture document) and `documents` (exactly the nine kinds below); a single-document task returns only its requested `{kind,markdown}` object; a review task returns its specified findings schema. Each companion document has ONLY `kind` and `markdown`. Never return filenames, paths, commands or approval flags. The eventual complete package contains all ten documents below. The server owns filenames and writes them together as one immutable revision.

Every document begins with scalar SmartMD frontmatter (`---`, nonempty `title`, `locale: ko` or `en`, `style: smartmd`, `---`). Use supported SmartMD callouts and tables where they help the specific document. The principal document includes a scope/uncertainty callout and a SmartMD table specification followed by a real GFM table. Write the body in the requested language; the exact H2 identifiers below are stable validation identifiers.

PRINCIPAL DOCUMENT: include `## Context and scope`, `## Method-R macro design`, `## Method-R system design`, `## Method-R module design`, `## Method-R detailed design`, `## Data and contracts`, `## Runtime and deployment`, `## Document map`, `## Open issues`. Use Method-R, not C4. Choose business-significant events before choosing diagram depth. At macro depth keep the target system ONE black-box object and describe its external actors/systems, business requests, results and independent notifications with `scope:` jobflow. External actions use `외부객체.On업무행동`, boundary messages use `객체.message.업무메시지`, and the receiving system owns business judgment/result branches such as `시스템.업무판정.결과 --> 상대.message.결과안내`; show the final result recipient. Keep common input validation in contract prose rather than inventing business branches. Do not expose internal UI/DB/schedulers in the macro object list. At system depth assign service/responsibility and single state owners with public contracts; a service boundary does not require distributed deployment. At module depth show the orchestrator wiring workers/gateways through narrow inputs/results/help callbacks; workers do not discover or call siblings. Expand uncertain/high-risk pieces recursively at detailed depth while preserving the parent input/result/error contract. Explain why a depth needs no further decomposition when that is the correct stopping point; do not invent four code layers. Important selected event flows use jobflow, including success/failure/unknown outcome and who learns the final result. Use source-grounded Korean business names in macro/system views; DSL keywords remain unchanged. Distinguish orchestration from choreography and from the transport mechanism. List shared cross-cutting capabilities once with lifetime/injection/failure policy rather than drawing logging arrows everywhere. Mermaid may supplement data/deployment views but must not replace Method-R collaboration or introduce a C4 structure. Link all nine companion documents in Document map with their exact filenames and link the detailed task diagrams in 잡플로우.md. Do not duplicate all companion content or repeat diagrams just to fill space.

MODULE DIAGRAM LOCATION: Keep the principal macro `scope:` Jobflow in `## Method-R macro design`. The module collaboration may instead live once in 잡플로우.md: either include an `orchestrator:` Jobflow in `## Method-R module design`, or put an explicit inline Markdown link such as `[모듈 협력](잡플로우.md#actual-task-heading)` in that module section. Use a single-line text label and a bare or angle-bracket destination without an optional link title for this delegation link. The linked real heading's own scope, ending at the next heading of equal or higher level, must contain the relevant `orchestrator:` Jobflow. A filename without an anchor, a link in another principal section, a code example, an image, an escaped link, an unrelated heading or a `scope:` boundary diagram does not satisfy this requirement. Do not duplicate the same module diagram merely to satisfy both locations.

DRIVERS: include `## Business goals`, `## Requirements and constraints`, `## Architectural drivers`, `## Scope and exclusions`, `## Evidence and open questions`. Define stable `### DRV-001 ...` headings. For each driver give source/evidence, type (core function, quality or constraint), priority, why changing it would change structure/ownership/deployment/important decisions, and the affected quality/decision references. Separate ordinary requirements from drivers using project-specific reasoning. A UI/menu change is not universally a non-driver; assess its impact in this system. State the first release boundary and excluded work as confirmed, proposed or unknown.

QUALITY SCENARIOS: include `## Quality scenarios`, `## Priority and acceptance`, `## Measurement and unknowns`. Define stable `### QA-001 ...` headings. Each scenario identifies driver(s), stimulus source, stimulus, operating environment, affected artifact, required response and response measure. Include the workload and measurement boundary where relevant. Separate hard invariants from negotiable targets. A proposed P95/SLO/throughput/recovery target is not a user requirement or measured result. If a number is unknown, record it as unknown and provide a concrete measurement method, proposed responsible role, decision condition and affected design choice. Discuss relevant correctness, security, availability, maintainability and performance by project risk rather than listing every quality attribute mechanically.

ALTERNATIVES: include `## Style and boundaries`, `## Tactics and patterns`, `## Alternative comparison`, `## Trade-offs and rejection`, `## Validation before choice`. Define stable `### ALT-001 ...` headings. Distinguish system-wide style from a quality tactic and from a concrete pattern. For each significant decision compare at least two materially different options, including the simplest viable baseline. Explain positive and negative effects against named DRV/QA references, consistency, availability, operational burden, cost and team constraints as relevant. Explain exclusions rather than silently omitting a candidate. A hard constraint cannot be traded away for an average score. Do not prescribe Redis, Kafka, microservices, distributed locks, PostgreSQL or AWS without project evidence. State the needed experiment and decision threshold where the trade-off is unresolved; do not fabricate benchmark results.

DECISIONS: include `## Decision records`, `## Decision dependencies`, `## Revisit conditions`. Define stable `### ADR-001 ...` headings. Each ADR records status, context, DRV/QA and ALT references, options considered, proposed decision or explicit deferral, rationale, gains, accepted drawbacks, mitigations, validation and reconsideration triggers. Use proposed/deferred when the user has not accepted a decision. Only source-backed explicit acceptance can justify an accepted status. Distinguish the selected strategy from the record explaining why. Cross-reference coupled decisions and conditions that would invalidate the choice.

DELIVERY: include `## Implementation sequence`, `## Verification matrix`, `## Operations and recovery`, `## Open decisions`. Define stable `### VAL-001 ...` headings. Link verification to DRV/QA/ADR and acceptance scenarios. Describe test inputs, environment, observable pass/fail criteria and required evidence. Include relevant negative cases, observability, rollback/recovery and responsibilities. Split implementation by cohesive ownership and dependencies. Mark unknown infrastructure, capacity, recovery targets and owners explicitly rather than substituting a boilerplate deployment plan.

DIAGRAM DOCUMENTS: retain the dedicated lowercase `navigation`, `jobflow`, `state`, `layout` DSLs; Mermaid supplements rather than replaces them. Navigation uses `## Navigation`, jobflow `## Jobflow`, state `## State`, screen_layout `## Screen Layout`. Include meaningful diagrams for each important task/owner/scene; the number follows actual scope and risk, not a fixed one-diagram limit. Every diagram has an explanation of its scope, assumptions, inputs/results and relevant failure/cancel/retry/return behavior. Navigation scenarios include screen verification tables with actual Layout anchors in `화면설계.md`. No HTML prototype is generated by this package: state that HTML is unavailable rather than linking nonexistent assets. State owners, initialization, inputs and invariants beside state diagrams. Explain each jobflow arrow in order. Screen layouts inventory pages and important scenes; explain action/data/error/empty/loading/accessibility and responsive behavior. A confirmed non-UI project retains Navigation/Screen Layout documents with explicit applicability, source-grounded reason and alternative CLI/API/batch interface. Unknown UI is not confirmed non-applicability.

TRACEABILITY: DRV, QA, ALT, ADR and VAL IDs are defined by real level-three headings in their owning documents; use unique three-digit IDs and refer only to defined IDs in the eventual complete package. During ordered single-document generation, a future owner's reference is a pending definition obligation under the single-document rules; that owner must define it on its turn, and every reference must resolve before the complete package is accepted. Link each QA to a driver, alternatives to DRV/QA, ADRs to their driver/quality/alternative basis, and verification to QA/ADR. Preserve known requirement/evidence IDs from the conversation and explain where a statement is a proposal. Use plain, unformatted heading text for portable anchors. Relative Markdown links may target only the ten server-owned filenames, optionally with an existing heading anchor. Do not invent source files, endpoints, evidence, screen captures, approvals or test results.

PORTABLE MARKUP: Raw HTML blocks are not supported in newly generated packages. Do not wrap document sections in `<pre>`, `<div>`, `<script>` or other block tags, standalone opening/closing HTML tags, processing instructions or declarations. Use actual Markdown headings and SmartMD directives; put HTML examples in fenced code. Ordinary comparison text, inline code, indented/fenced code examples and inline emphasis/span tags within a paragraph may remain. HTML comments and code examples cannot satisfy sections, trace definitions or diagram requirements. Historical stored drafts are not revalidated under this new restriction.

DEPTH AND SKIPPING: The user may draft before completing the interview. This changes certainty, not the obligation to analyze the design. Keep unresolved facts visible, compare conditional alternatives and identify what evidence chooses between them. Do not collapse the package into a generic MVP summary, replace reasoning with technology lists, or repeat the same paragraph across files. A small project can have concise documents, but each important choice still needs a driver, quality consequence, alternatives, rationale and verification. Do not copy the ticketing lecture's example traffic, SLO, database or cloud into another project.

REVIEW: The independent critic reads the entire package. Check evidence, distinction between drivers and ordinary requirements, measurable quality scenarios, feasible alternatives, trade-offs against hard constraints, proposed/accepted status, traceability, diagram consistency and unresolved decision conditions. Findings refer to the affected filename and IDs. Do not declare all documents reviewed if any companion was omitted from the review context.

PORTABLE SMARTMD AND DIAGRAM SYNTAX

These are syntax examples, not project facts. Substitute the project's actual or explicitly proposed names and contracts. Do not invent DSL keywords. Dedicated fences open and close at column zero, with the lowercase language immediately after the opening backticks; put each DSL in the owning section described above, outside callouts and example fences.

SmartMD callouts use `:::info title="Scope and unknowns"` or `:::warning title="Unresolved choice"`, followed by nonempty prose and a standalone closing `:::`. Supported kinds are info, warning, note, tip, success and danger; do not nest callouts. A table specification is outside code and immediately before the matching real GFM table, for example:

navigation: `Page --> OtherPage : action`, `Page --> (validate_input)`, `(validate_input) --> (/actual_api) : valid`, `(/actual_api) --> Page : error`. Separate labels with spaces around ` : `. Only pages, `(process)`, `(/api)` and backtick-wrapped data are nodes; User/Browser/Email actors and event nodes do not belong here. Use simple node names without square/curly brackets, pipes or semicolons. Explain direct URL entry and single-page tasks in prose instead of inventing self-arrows. Label unsourced API contracts as proposals. Screen-verification tables use `페이지·장면 | 화면 HTML | Layout`, record `확인 불가 — 화면 HTML 미생성` for HTML, and link Layout cells to actual headings in 화면설계.md.

jobflow: start with `scope: public cooperation` for a boundary view OR `orchestrator: Coordinator` for a coordinating owner. Declare all objects once with `Object: A, B, C` in readable order. Arrows use `A.Method --> B.Method`, `A.OnEvent --> B.Method`, `A.Check.true --> B.Method`, or `A.message.Request --> B.message.Response`. No arrow labels, parameters, invented comments or extra control tokens. Explain every arrow immediately below in declaration order; distinguish calls, events, returned results and boundary messages. Macro/system object and method names use the project's business language; the principal Method-R rules take precedence over these abstract syntax names.

state: `<s> --> (Ready)`, `(Ready) --> (Running) : input`, `(Running) --> (Failed) : failure`, `(Failed) --> (Ready) : retry`. Parenthesized nodes are states, `<Event>` is an event, plain text is an action. `<e>` or `.` is a real lifetime end; do not terminate a continuing service merely because one task finishes. Use simple node names and explain complex conditions beside the diagram. State ownership, initialization, transition input, invariants and forbidden transitions stay consistent with the other views.

layout: each block is ONE connected tree. `Screen V Header, Main, Footer`, `Main > Sidebar : 25, Content : 75`, `Content V Input, Result`. ` V ` means vertical; ` > ` means horizontal. Children are comma-separated; optional numbers are horizontal flex weights without `%`, not pixels. No H operator, cycles, duplicate containers, multiple parents or disconnected roots. Explain scene-specific loading, empty, success and failure behavior outside the block.

Confirmed non-UI exceptions in Navigation and Screen Layout use these three standalone fields, with source-grounded values in the requested language:
Applicability: not_applicable
Reason: a concrete explanation grounded in the supplied source
Alternative interface: the actual or explicitly proposed CLI/API/batch/operator interface and its contract
Jobflow and State always need meaningful DSL. A confirmed single-page UI with no page movement may use the exception in Navigation only, explaining the same-page tasks and linking its actual Layout. Unknown UI is not evidence for an exception.
